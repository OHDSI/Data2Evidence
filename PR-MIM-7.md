Ticket: [MIM-7](https://gesundheitscloud.atlassian.net/browse/MIM-7)

Adds a JupyterHub that logs people in with their existing D2E account
(only lets in those who hold the `role.jupyteruser` role in Logto)

---

## What happens when someone logs in

```
 browser
   │  1. open the hub, click "Login with D2E Logto"
   ▼
 JupyterHub ──2. send the browser to Logto──▶ Logto (D2E's own, used as-is)
   │                                              │ 3. user signs in, consents
   │◀─────── 4. back with a one-time code ────────┘
   │
   │  5. the hub itself exchanges that code for tokens, server to server
   │  6. checks the role in the token, then creates that person's notebook
   ▼
 jupyter-<username>
```

Step 2 needs a URL the browser can reach; step 5 is container-to-container and
uses caddy's internal listener, so the hub needs no D2E certificate installed.
Same split WebAPI already uses.

## How a Logto role becomes an access decision

```
role "role.jupyteruser" in Logto - Logto maps a role to a scope of the same name
   ▼
scope on the alp-default API resource
   ▼
token response: {"scope": "role.jupyteruser"} - granted_scopes() turns granted scopes into JupyterHub groups
   ▼
JupyterHub group "role.jupyteruser" - allowed_groups gates on it; allow_all=False
   ▼
allowed, or 403
```

`allow_existing_users = False`, so the role is re-read **on every login**.
Revoking it in Logto blocks the next login even though the user and group are
still in JupyterHub's database.

## changed files

#### `docker-compose.yml`

1. **`role.jupyteruser` added to `LOGTO__ROLES`, `LOGTO__SCOPES` and
   `LOGTO__ROLES_SCOPES`.**
2. **The JupyterHub application, added to `LOGTO__CLIENT_APPS` only when
   `LOGTO__JUPYTERHUB__CLIENT_SECRET` is set:**

   ```yaml
   LOGTO__CLIENT_APPS: '[${LOGTO__JUPYTERHUB__CLIENT_SECRET:+{"name":"jupyterhub", ...},}{"name":"alp-svc", ...unchanged... }]'
   ```

   `${VAR:+...}` expands to nothing when the variable is unset, so a deployment
   that does not run JupyterHub renders this line byte-identically to `develop`
   and creates no application. Verified both ways with `docker compose config`.
   The callback URLs follow `JUPYTERHUB__PUBLIC_URL`, which the overlay also
   hands to the hub, so the registered redirect URI and the hub's own callback
   cannot drift apart.

#### `docker-compose-jupyterhub.yml`

to make local jupyter container

```sh
docker compose -f docker-compose.yml -f docker-compose-jupyterhub.yml up -d --build
```

An overlay, not a standalone stack — `alp` and `PROJECT_NAME` come from
`docker-compose.yml`. It also derives everything the hub cannot start without
(client id and secret, callback, Logto endpoints, role) from the stack's own
variables, and defines the Docker API proxy and the isolated notebook network.

#### `services/jupyterhub/jupyterhub_config.py`

the env configuration is here for mapping. Three settings are non-obvious:

- `LOGTO_USERNAME_CLAIM=username` — Logto advertises `preferred_username` but
  never populates it, and `email`/`name` are `null` for the seeded admin.
- `resource=https://alp-default` is sent with the request — without it Logto
  omits the scopes and **everyone** is rejected, including role holders.
- `Authenticator.auth_refresh_age = 0` — oauthenticator's periodic
  re-validation decodes the *stored* id token with `exp` on, so ~1h after login
  it 500s and every request fails with "Missing or invalid credentials".
  Authorization only depends on the check at login, which is unaffected.

#### `services/jupyterhub/logto-role.py`

grant/revoke/list of `role.jupyteruser` through Logto's management API.
Needed because the Logto admin console is commented out in this stack's
Caddyfile, so there is otherwise no way to perform the one operation that
decides who can use JupyterHub. It runs in a throwaway container on the D2E
network with the directory mounted read-only, so nothing is copied into a
running container and it needs no image of its own. Becomes unnecessary once
access is driven by an IdP group.

`role.sh` at the repository root wraps it:

```sh
./role.sh list
./role.sh grant <username>
./role.sh revoke <username>
```

It reads the Logto management credentials from the running Logto container, so
nothing has to be exported, and resolves paths from its own location rather
than `$PWD`, so running it from the wrong checkout fails with a message naming
the problem instead of mounting an empty directory. `LOGTO_CONTAINER` and
`NETWORK` point it at another deployment.

## How to run it

Needs an `.env` generated by a current `d2e init`.

**1. Enable it.** One variable. Setting it registers the OIDC application and
turns the hub on; leaving it unset changes nothing anywhere.

```sh
echo "LOGTO__JUPYTERHUB__CLIENT_SECRET=$(openssl rand -hex 32)" >> .env
```

**2. Start it.**

```sh
docker pull quay.io/jupyterhub/singleuser:5.4.2   # else the first spawn waits on ~1.5 GB
docker compose -f docker-compose.yml -f docker-compose-jupyterhub.yml up -d --build
```

On a stack that is already running, register the application separately. The
seeding container is one-shot and idempotent, and also creates
`role.jupyteruser`:

```sh
docker compose up alp-logto-post-init
```

**3. Give someone the role.**

```sh
./role.sh grant <username>
./role.sh list
```

**4. Log in** at <http://localhost:8000> and press **Start My Server**.

`services/jupyterhub/.env` is optional and only for tuning — crypt key,
resource limits, notebook image, logout behaviour. Set `JUPYTERHUB__PUBLIC_URL`
when the hub is not on `http://localhost:8000`.

> Sign in to the D2E portal (<https://localhost/d2e/portal>) first. The portal is
> this deployment's login surface: Logto's `/sign-in` redirects there whenever
> there is no interaction session, because the seeding sets
> `unknownSessionRedirectUrl`. Arriving at JupyterHub cold can land on a blank
> `/sign-in` page; with a Logto session the hub skips it entirely.

## Security notes

**Notebooks are isolated from the D2E network.** A notebook is arbitrary user
code. Spawning notebooks onto the D2E network — the obvious configuration, and
what this branch did at first — gave every JupyterHub user a route to
`d2e-minerva-postgres-1:5432`, `d2e-logto-1:3002` (Logto's management API),
Redis, trex and demodb. Notebooks now join `jupyterhub-notebooks` and nothing
else; measured from a live notebook, those names no longer resolve and only
`d2e-jupyterhub:8081` answers. If notebooks later need D2E data, expose the one
service they need rather than putting them back on `alp`.

**The hub does not hold the Docker socket.** Mounting `/var/run/docker.sock`
into the hub is equivalent to giving it root on the host, so the socket goes to
`docker-socket-proxy` instead, on an `internal` network shared with the hub
alone and publishing no ports. It allows the container, image and network reads
the spawner needs and refuses the rest — `/info`, `/secrets`, `/nodes` return
403, and `EXEC` in particular is refused, since it would allow running commands
inside any container on the host.

This **does not make DockerSpawner safe**: whatever reaches the proxy can still
create containers, and container creation can be abused to mount host paths. It
reduces the blast radius from *root on the host* to *can create containers*. The
alternatives are `SystemdSpawner`, giving up container isolation, or
`KubeSpawner`, needing Kubernetes.

**The hub-to-Logto token exchange is in clear text**
(`http://d2e-caddy:8080/oidc/token`). That is this stack's existing convention
and there is no alternative here: Logto listens only on plain HTTP and caddy's
only TLS listener carries a `localhost` certificate. It stays inside one host's
Docker network. **It is not acceptable once the hub runs on a separate VM** —
that needs the public HTTPS endpoint plus certificate trust in the image, and
the JupyterHub VM must not be joined to the D2E network to avoid it, since that
reinstates the exposure removed above.

**Logout is partial.** `/hub/logout` clears the hub cookie, and
`LOGTO_END_SESSION_URL` additionally drops this client's grant so consent is
requested again, but neither ends the Logto account session — that needs an
`id_token_hint`, which a static `logout_redirect_url` cannot carry. Pressing
Login again signs the same user straight back in without a password.
`JUPYTERHUB_SHUTDOWN_ON_LOGOUT=true` does work and stops the notebook container.

**Applications cannot be created through Logto's management API here.**
`POST /api/applications` returns 500 and leaves a half-created row with no
secret, because `logto.check_application_type()` is pinned to
`search_path=public` while its body queries `applications` unqualified, and D2E
keeps Logto's tables in the `logto` schema. A secret stored as `#internal:...`
is such a row. This is why registration goes through compose. Possibly worth
its own issue.

## Open decisions for reviewers

1. **Docker socket exposure** — reduced as described, but this needs sign-off
   rather than review.
2. **Real single logout** — needed before shared machines, or accepted and
   communicated.
3. **Reading D2E data from notebooks** — the network is closed now. Enabling it
   means passing the token into the notebook and opening one specific service.
4. **User management** — per-user grants, or mapping an existing IdP group.
   D2E already supports the latter through `LOGTO_ROLES_AZ_GROUPS_MAPPING`,
   which would remove the per-user administration entirely.
5. **Notebook image** — whether the standard `singleuser` image is enough or
   OHDSI R packages and database drivers are needed.
